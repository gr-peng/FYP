# Bybit 主动成交外部诊断：实施前设计

日期：2026-10-11。状态：研究设计，尚未实现或运行本诊断。本文不宣称当前全量重审通过，也不引用事件检验期市场统计。已有代码版本 `f7f0d2e` 的工程修复和工程测试不能代替以下外部验证。

## 研究问题与可识别范围

使用同场所、同品种的2024年11月 Bybit BTCUSDT USDT线性永续500档L2与逐笔成交，检验：**在给定真实某笔成交的主动方向和数量后，成交前已生成的可见盘口能否解释其成交价格；误差如何随盘口年龄、可见深度和时间对齐假设改变。** 这是条件化的执行价格诊断。该笔真实方向和数量是事后观测的输入，不是模型在成交前已经预测出的订单。

500档档案在已做的格式探测中约每100ms更新，逐笔成交可能在两个盘口消息之间发生多次；不能把档案当作每次撮合之前的完整状态。该数据是中心化交易所聚合盘口，不是链上逐单账本。当前官方深度及频率列表已经变化，不能拿当前列表替代2024年的档案制度。

本诊断可发现方向颠倒、数量尺度错误、显著时间错位、使用未来盘口、错误逐档成本和可见数量覆盖不足，也可量化观测限制。即使结果很好，也不能单独验证整张主动订单的成交比例、取消/拒绝概率、成交等待时间、实际网络延迟、冲击响应或被动队列。

## 为什么不能把逐笔当作整张主动订单

公开成交协议给出主动方 `S`、数量 `v`、价格 `p`、成交ID `i`；没有把执行关联到完整主动订单的 `orderId`。私有执行协议另外提供 `orderId`、`orderQty`、`leavesQty`、`execId`，并明确同一订单可以产生多次执行。这直接支持“公开逐笔不等于整单”的区分。[公开成交文档](https://bybit-exchange.github.io/docs/v5/websocket/public/trade)，[私有执行文档](https://bybit-exchange.github.io/docs/v5/websocket/private/execution)。

以下为构造例子，不是历史数据结果：卖盘为1 BTC @100和1 BTC @101，一张主动买入2 BTC的订单产生1 BTC @100、1 BTC @101两笔成交。若对每笔的1 BTC都独立扫同一份事前盘口，预测都会是100，第二笔出现误差；真实整单VWAP却正好是100.5。误差来自未知的整单结构，不足以证明sweep规则错误。相反，一笔成交的数量也可能小于该价格档的总可见量，不能把它当成该档被吃完的证据。

同时间戳、同方向或相邻成交ID不构成同一主动订单的证据：它们可能来自多个订单，同一订单也可能跨时间戳执行。当前公开协议的 `seq` 也不能替代订单ID；当前文档允许相同 `seq` 出现在多条消息中。2024年归档CSV本身没有 `seq`。不得把人为合并的成交簇叫作恢复出的真实订单。

第一版逐笔独立对历史盘口做只读sweep，不从历史簿永久扣除真实逐笔数量。否则随后再应用真实绝对深度增量，可能重复处理同一次执行；补挂单、撤单和两次推送间的未观测变化也不能由逐笔唯一分解。任何“根据成交依次扣减”的替代模型必须作为另一个带假设的估计器单独登记，不能混入本诊断的真值。

## 固定对齐规则：先可用，再比较

重放原始LOB消息，不能使用现有按秒特征作为逐笔的事前盘口。秒末状态可能包含该笔成交之后的消息，且秒桶的确认时间可能更晚。原始消息级状态不需要等到秒结束，但必须等到构成状态的所有依赖消息都已可用。

设有效segment内消息依原始顺序编号为 `j`，从snapshot开始：

```text
prefix_ts_ms[j] = max(ts_ms[k] for k from segment snapshot through j)
publication_upper_us[j] = (prefix_ts_ms[j] + 1) * 1000
engine_upper_us[j] = (cts_ms[j] + 1) * 1000
eligible(j, trade, delay_us) =
    valid_state[j]
    and publication_upper_us[j] + delay_us < trade.timestamp_us
    and engine_upper_us[j] < trade.timestamp_us
```

加1ms并使用严格小于，是预先选择的保守量化规则，排除无法判定先后的同毫秒边界；不是官方给出的额外延迟。每筆使用按原始订阅顺序可达的最近合格状态。保留状态依赖的最大 `ts`，不能只用最后一条delta的 `ts`。新snapshot替换整本并开始新的segment。原始序列中的尚未可用消息构成推进屏障，不能跳过它去应用后续delta或选择更有利的盘口。

`cts` 单调性、快照重置、缺口处理沿用 `BybitBook` 与当前审计规则；`seq` 不要求加一。无有效snapshot、已知缺口后未恢复、单边为空、交叉簿或非法精度均不得产出该状态的预测。单次 `u` 连续也不等于已证实档案包含所有真实事件。对已到达可用时刻的异常消息立即使当前状态失效，等新的有效snapshot恢复；不能继续拿失效前的盘口冒充当前有效状态。

第一版预注册附加 `delay_ms = [0, 10, 50, 100, 250]`，0为主报告，其余全部报告敏感性，不按误差选择“真实延迟”。这是额外信息滞后的假设，不能从中分离行情传输、决策、发单传输的实际贡献。即使0ms结果好，也只支持服务端消息时间代理下的条件关系，不证明真实交易者能使用这份盘口。

盘口年龄记为 `trade.timestamp_us - 1000 * cts_ms`；固定分层为 `[0,25)`、`[25,100)`、`[100,250)`、`[250,1000)`、`[1000,+∞)` ms。主价格误差报告使用年龄小于1000ms的合格状态；更旧状态单独报告，不删除其数量。1000ms只是事先固定的陈旧状态筛选，不是从本数据估计的市场常数。所有延迟设置同时报告各自覆盖率；比较延迟影响时另列所有设置共同合格的交集样本，防止因样本改变产生假改善。

日文件尾部次日约2秒消息只参与既有格式完整性检查。诊断成交时间、被用状态的 `cts` 与可用时刻都必须落在所选UTC日内；不从前一天继承已知状态，也不从次日借确认消息。±60秒审查容差不能扩展诊断日期。每天从该日有效snapshot重新建立状态，开头不可用部分记入排除计数。

## 预测量、基线与不可用结果

对每个合格逐笔，以其主动方向和精确整数数量运行已有 `BybitBook.sweep()`：买单消耗卖盘，卖单消耗买盘。只读结果记录逐档使用量、覆盖量与余量。价格乘100、数量乘1000为存储尺度，不据此断言历史最小交易步长。整数积 `sum(price_units * quantity_units)` 的尺度为100000，保留分子分母计算VWAP，最后展示时才转小数。

固定比较以下三个同信息集结果：

1. **可见深度sweep**：以已知逐笔数量求可见簿VWAP。
2. **最优对手报价**：买用最优卖价，卖用最优买价；检验深度建模是否比最简单可成交报价增加解释力。
3. **中间价**：同一状态的bid/ask平均，仅作忽略价差的参照，不叫可执行报价。

CSV没有逐笔消息发布时间，因此“前一笔成交价”不能在主报告中声称是成交前已发布的基线。如后续加入，只能单独标注为成交时间对齐的参照，不能混入相同可用信息集的结论。

主价格误差只在sweep覆盖全部目标数量、三个基线均存在的同一组样本上成对比较。对未覆盖部分，不外推末档价格、不假设全成；记录 `covered_quantity_units`、`unresolved_quantity_units` 和部分可见成本，但不把部分VWAP与整笔成交价混成完整预测。可见数量覆盖比例不是实际订单成交率。

按 `quantity_units / opposite_l1_quantity_units` 分成 `≤1`、`(1,5]`、`>5`，另列超过可见总数量的样本。在 `≤1` 组，sweep应与最优对手价一致；这组的高准确度不足以支持跨档模型。必须单独报告跨L1档样本的数量、覆盖与成对误差。不得因这些样本难解释而按误差过滤，也不能把真实成交价作为sweep的限价输入。

每笔保存绝对价差、绝对bps误差和方向调整的残差：

```text
s = +1 for taker Buy, -1 for taker Sell
signed_residual_bps = s * (observed_price - predicted_price) / predicted_price * 10000
```

正值表示真实成交比该预测更不利。主报告给出成对MAE、median/p90/p99绝对bps误差、最优对手价与sweep的误差差值，以及按盘口年龄、方向、数量层、延迟设置分层的覆盖计数。整数表示下的精确价格相等可作为诊断项，不能称为已验证的历史tick命中率。所有表均先给候选成交数、全部排除原因计数及最终分母，避免只展示容易预测的子集。

## 留出与“独立样本”的定义

一条trade不是一个独立试验。同一未观测主动订单、同一盘口状态和同一时间簇可能贡献多条trade；连续消息也受同一市场状态影响。第一版保留全部合格逐笔，存储 `(day, segment_id, book_message_index)` 与逐笔时间戳的簇标签，不随机拆分trade，也不把簇标签当作真实订单标签。

独立于参数制定的评价样本是预先留出的11月4日完整时间段，而不是训练数据里随机抽出的成交。它只构成一个开发日，不能因此断言跨日期或跨事件的独立同分布泛化。若查看其结果后修改规则，修改次数和版本必须记录，开发日不再是新版本的未见数据。

报告以不重叠5分钟UTC时间块汇总成对损失，按日展示块分布与日汇总；逐笔加权指标同时作为不同权重的描述结果。空块保留覆盖记录，不填零误差。不把数百万成交数用作置信区间的独立样本数。五分钟块仍可能相关，不能仅因不重叠就叫作IID；第一版不作基于独立trade假设的显著性检验。只有三个训练日和一个开发日，任何区块重采样区间也只能标为有限样本描述，不能据此证明真实填单模型成立。

## 最小实现方案与运行门控

拟新增 `experiments/bybit_execution_diagnostic.py`、`scripts/run_crypto_execution_diagnostic.py` 和对应语义测试；以下是待实现接口，不表示这些文件已存在：

```text
run_execution_diagnostic(root, source_config, diagnostic_config,
                         split in {train, development}, days, output_dir)
```

实现顺序固定为：

1. **输入授权与溯源。** 写入本次 `running`/不可消费状态后再做预检查；核对冻结配置hash、日期、品种、本次逐文件审计 `status=complete`、`audit_run_id`、原始文件实际字节hash/长度与元数据。ZIP/GZIP必须已有完整EOF/CRC验证；成交质量必须valid，LOB仅用审计认可的有效segment。拒绝旧的 `initial_ec620a4_audit` 结果。拒绝 `event_test`，包括通过任意路径绕过日期选择。预检查失败也发布本次failed，不能保留旧成功授权。
2. **使用原始消息而非秒特征。** 本诊断的授权应绑定原始审计和有效segment，不能把 `features_published` 当作已验证原始流的充分条件。若实现另外消费任何派生特征，仍须通过现有消费者的 `features_published`、特征hash/行数等门控；不绕过或放宽该消费者。没有当前原始审计证明时，本诊断不能运行，即使旧Parquet存在。
3. **有序双流扫描。** 逐笔按原CSV顺序读取，保留同timestamp行序；盘口按原消息顺序推进至其可用时刻严格早于当前成交。只保留当前book和必要计数，读消息前瞻只为确定推进边界，不读取未来价格作为预测特征。第一版每个delay独立流式扫描，减少多版本状态管理错误；不得为速度静默排序、去重或合并整单。源文件已通过完整审计且实际字节hash匹配时，冒烟可只评分固定窗口，不能把仅扫描窗口说成重新验证了全文件CRC。
4. **只读预测与逐笔出处。** 每行至少存trade ID/原始行号、UTC日、整数时间/方向/量/真实价、book原始行号/segment/u/seq、`cts`、累计最大 `ts`、假设延迟、盘口年龄、对手L1/可见量、覆盖及余量、成本分子/分母、基线、排除原因。先生成当前行预测再读取它的价格标签计算分数；同一时刻成交沿用可用盘口，不通过真实成交价格修正历史簿。
5. **原子发布。** 流式写临时逐笔Parquet及5分钟块表，再生成摘要和manifest。manifest绑定代码版本与工作区变更状态、两份配置hash、输入hash、审计run ID、日期/延迟/窗口、输出hash/行数。任何失败都不发布本次可消费结果；完成状态只证明诊断执行成功，不表示研究假设已通过。

预定输出位于 `outputs/crypto_microstructure_20261011/execution_diagnostic/<run_id>/`，按日和delay分区。逐笔表可大于摘要，不能省略失败分母；绘图和摘要直接读取经manifest验证的表，不读取任意旧路径。

## 编码前冻结的验收项

以下是拟实施的测试与检查，不是已通过成绩：

- 构造两档sweep，验证整数成本、买卖方向、部分覆盖与余量；验证只读调用不改变后续历史簿。
- 使用“2 BTC整单拆成两笔”的例子，验证程序不会自行合并或把第二笔误差归因为已证实的撮合错误。
- 改变未来盘口价格/数量，当前预测必须不变；同毫秒边界被保守排除，不能取包含该笔成交结果的后验盘口。
- 构造晚 `ts` 后接较早 `ts` 的delta，验证累计可用时间与原序列屏障；构造snapshot重置和缺口，验证恢复前不产生有效状态预测。
- 精确微秒时间、相同时间不同trade ID、重复ID、逆序/截断/CRC失败按既有质量审计拒绝，不通过排序或去重修复。
- 延迟敏感性同时验证各自样本和共同交集样本；缺状态、陈旧状态、可见量不足都有明确分母。
- 日界后消息不得进入当日预测；`event_test`、越权日期、修改后的原始字节、失败预检查留下的旧manifest均被拒绝。

工程验收通过后，先报告所有训练日覆盖率、分层误差及失败原因，再按冻结设计运行开发日。暂不规定一个任意“误差小于X即真实”的阈值：需要先明确可识别目标，并依据训练日变异制定后续可检验假设。诊断结果好或差，都不能单独决定完整fill模型已经通过或失败。

## 完整成交验证仍缺什么

若要从本诊断升级为整单执行验证，至少需要能把执行映射回主动订单的订单ID、提交数量/限价/有效期、所有执行及剩余量/终态，以及订单发出、确认和行情接收的可比时间；有这些记录才能评价整单VWAP、未成交比例和等待时间。私有执行接口表明部分字段确有官方定义，但当前项目没有相应历史账户记录，本文未调用账户接口或发起交易。

验证被动队列还需要逐单生命周期、优先级规则或有约束的队列假设；验证冲击需要订单改变市场后续状态的额外识别设计。500档L2加公开trade tape不能自动补齐这些信息。当前最短可靠路线是先完成本条件诊断、量化可见数据的解释力，再决定是否值得寻找带订单关联的研究数据或用户已持有的执行记录。

文中官方网页于2026-10-11核验，说明的是当前公布的字段语义。所有涉及2024年档案字段、时钟及制度的历史等价性均按上述限制处理；不会把当前文档新增字段、深度频率或RPI规则反填到历史数据。
